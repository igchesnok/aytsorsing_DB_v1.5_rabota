ОПЛАТА РАБОТ — «НЕ РАСПРЕДЕЛЕНО» + ПАНЕЛЬ ШАГОВ РАБОТЫ С ПЛАТЕЖКОЙ (T106)
==========================================================================
База: aytsorsing_DB_v1.5_rabota со всеми правками вплоть до T105
(страница «Оплата работ» T102–T105 обязательна).

ЧТО СДЕЛАНО
-----------
1. «НЕ РАСПРЕДЕЛЕНО» вместо «Распределено по позициям»
   Оператор распределяет СВОБОДНЫЕ средства платежки, поэтому главным
   индикатором стал остаток, который ещё можно распределить:
   • строка формы: «Не распределено (без НДС): Z ₽ · распределено X из
     Y ₽ (без НДС)» — живой пересчёт при вводе суммы и распределении;
     отрицательный остаток подсвечивается красным;
   • таблица «Оплаты по выбранной операции»: колонка «Распред. ₽»
     заменена на «Не распр. ₽» (= сумма платежки без НДС − распределено);
   • модалка распределения: живой контроль дополнен остатком —
     «Распределено: X из Y ₽ (без НДС) · Не распределено: Z ₽»;
   • сервер: GET /api/oplata/zapisi отдаёт ne_rasp по каждой платежке.

2. ПАНЕЛЬ ПОСЛЕДОВАТЕЛЬНЫХ ШАГОВ РАБОТЫ С ПЛАТЕЖКОЙ (эталон — страница
   «Заказы по договорам»; бейджи 1-2-3-4, серые = заблокирован,
   оранжевый = активен, зелёный = выполнен)
   Шаг 1. «Прикрепить PDF платёжного документа» — кнопка «📎», только
          PDF (лимит 25 МБ), файл хранится в public/uploads/oplata/,
          путь — в oplata_rabot.ssylka_doc; есть ссылка на файл и «✕»
          для удаления.
   Шаг 2. По типу оплаты:
          • «Предоплата (аванс)» — «Отправка документа на почту»:
            НОВОЕ поле «Email» (можно несколько адресов через «;»),
            кнопка «✉ ➜» отправляет прикреплённый на шаге 1 PDF письмом
            (подпись — общий блок Чеснокова И.И.). Факт отправки
            фиксируется: oplata_rabot.email_otpravki (адреса) +
            data_email_otpravki (дата/время).
          • «Окончательный расчёт» — «Занесение акта в 1С»: дата
            «Дата занесения в 1С» (oplata_rabot.data_vneseniya_1s).
   Шаг 3. (только окончательный расчёт) «Реестр платежей» — «🖨
          Распечатать реестр по шаблону» — ЗАГЛУШКА (показывает
          уведомление; печать по шаблону будет реализована позднее).
   Шаг 4. (только окончательный расчёт) «Скан подписанного реестра» —
          «📎 Прикрепить скан… (PDF)» → oplata_rabot.ssylka_scan_reestra,
          ссылка на файл + «✕».
   Гейты: шаг 2 открывается после шага 1; шаги 3 и 4 — после шага 2
   (шаг 3 — заглушка без состояния, шаг 4 не блокирует до появления
   реальной печати реестра). Для аванса шаги 3/4 скрыты.
   Панель доступна после сохранения платежки (клик по строке в таблице
   «Оплаты»); в режиме создания показывается подсказка.

3. НОВЫЕ ЭНДПОИНТЫ (сервер)
   PUT  /api/oplata/zapisi/:id/step  — поля шагов (белый список:
        ssylka_doc, ssylka_scan_reestra, data_vneseniya_1s,
        email_otpravki, data_email_otpravki; пути файлов только
        /uploads/oplata/…);
   POST /api/oplata/upload-file      — сырая загрузка PDF
        (?name=&kind=doc|reestr) → public/uploads/oplata/, только .pdf,
        лимит 25 МБ;
   POST /api/oplata/send-email       — отправка PDF платежки на почту
        { oplId, email } (нормализация адресов, проверка наличия файла
        шага 1, дата отправки пишется в БД).

4. БД (миграция выполняется автоматически при старте сервера)
   oplata_rabot + ssylka_doc, ssylka_scan_reestra, email_otpravki,
   data_email_otpravki (data_vneseniya_1s была с T102).
   Колонки добавлены и в схему новых БД, и миграцией для существующих
   (ensureColT106 в src/Database.js).

УСТАНОВКА
---------
1. Остановить сервер (порт 3110).
2. Скопировать 5 файлов поверх одноимённых в корне проекта
   (пути — от корня aytsorsing_DB_v1.5_rabota).
3. EOL в zip сохранены как в репозитории — копировать поверх, не
   пересохраняя редактором.
4. Запустить сервер — при старте миграция добавит 4 колонки в
   oplata_rabot (в логе: «✅ T106: колонка oplata_rabot.… добавлена»).
5. Открыть «Оплата работ», выполнить Ctrl+F5.

ПРОВЕРЕНО
---------
• HTTP-тесты T106: 35/35 — миграция колонок; частичное распределение и
  ne_rasp (1000 − 850 = 150; перераспределение → 800); превышение лимита
  (POST и privyazat) → 400; PUT step: чужое поле/чужой путь/нет оплаты →
  400/404; upload: не-PDF → 400, PDF с кириллицей в имени → 200 и файл
  на диске; send-email: валидация (без oplId / пустой email / кривой
  адрес → 400); сохранение data_vneseniya_1s, email_otpravki,
  data_email_otpravki, ssylka_scan_reestra.
• Браузные тесты T106 (Playwright): 52/52 — разметка («Не распределено
  (без НДС)» вместо «Распределено по позициям», панель шагов, PDF-inputs);
  автофильтры T104 (аванс → № эт.=1; окончательный → «Получение готовой
  продукции»); создание аванса: модалка, автозаполнение (30% от
  стоимости), «Не распределено: 0.00», колонка «Не распр. ₽»; шаги аванса
  (1 → done, 2 валидация email, скрытие 3/4); окончательный расчёт:
  предзаполнение T105 (Стоимость − оплаченный аванс = 252000/246411.2),
  частичное распределение («Не распределено» > 0), шаг 2 — дата 1С → done,
  шаг 3 — тост-заглушка, шаг 4 — скан → done; консоль чистая.
• Примечание: реальная SMTP-отправка в песочнице не выполнялась (нет
  доступа к сети) — проверены все ветки валидации; сама отправка
  использует тот же sendEmail() emailService.js, что и письма заказов.
• Регрессия T102/T103 API-тестов t102_api_test.py/t103_api_test.py не
  прогонялась: они используют ДО-T104 контракт (POST без pozSum,
  oplacheno «пусто» вместо 0) и были заменены на браузерные проверки в
  T104/T105. Вся цепочка T102–T105 (распределение, лимиты без НДС,
  предзаполнение, автофильтры, обязательные фильтры) покрыта тестами T106.
• БД песочницы восстановлена (платёжек нет), загруженные тестовые файлы
  удалены.
