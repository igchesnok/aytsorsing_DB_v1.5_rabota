t86 — РУЧНОЙ ВВОД ID ДОКУМЕНТОВ СЗ (ВКЛАДКА «ДОКУМЕНТЫ»)
=========================================================

ЗАДАЧА
------
На странице «Редактор транспортных операций» (вкладка «Документы») поля
ID документов — «ID СЗ на транспорт» (toSzTransportID) и «ID СЗ в СБ об
отгрузке» (toSzSbId) — были доступными только для чтения. Если служебная
записка ранее была создана ВРУЧНУЮ в вазовской системе ЭДО (docs.vaz.ru),
ввести её d_kod и сохранить в базе было невозможно: поле не принимало
ввод, а сервер при сохранении операции эти поля игнорировал.

ПРИЧИНА (ДВА БАРЬЕРА)
---------------------
1. Страница (transport-ops.html): у обоих полей стоял атрибут readonly —
   ввод заблокирован в браузере.
2. Сервер (transportOperRoutes.js, PUT /api/transport-oper/:id): список
   обновляемых колонок НЕ включал sz_transport_id и sz_sb_id — клиент
   отправлял значения (они и раньше уходили в запросе), но сервер их
   отбрасывал. Исторически эти поля заполнялись ТОЛЬКО автоматически при
   создании СЗ через систему («Создать»), ручной ввод не предусматривался.

ЧТО СДЕЛАНО
-----------
1. РАЗМЕТКА (transport-ops.html)
   • readonly снят у «ID СЗ на транспорт» и «ID СЗ в СБ об отгрузке»;
   • подсказка при наведении дополнена: если документ создан в ЭДО
     вручную — введите ID и сохраните операцию кнопкой «Редактировать».

2. СОХРАНЕНИЕ НА СЕРВЕРЕ (transportOperRoutes.js)
   • PUT /api/transport-oper/:id теперь записывает sz_transport_id и
     sz_sb_id вместе с остальными полями вкладки «Документы»;
   • значения обрезаются от случайных пробелов (trim) — пробел в начале
     ID иначе ломал бы ссылку на карточку документа
     (docs.vaz.ru/main.aspx?d_kod=…).

3. ВСЯ ОСТАЛЬНАЯ ЦЕПОЧКА РАБОТАЕТ С РУЧНЫМ ID КАК С ОБЫЧНЫМ
   • «Ред.» — открывает текст документа с портала по введённому d_kod;
   • «Откр.» — открывает карточку документа в браузере (docs.vaz.ru);
   • «Создать» корректно предупреждает «Письмо уже было создано» /
     «СЗ в СБ уже была создана» — двойное создание исключено (как в VBA);
   • «Удалить СЗ» — удаляет документ в системе ВАЗ и очищает поля;
   • строка «Файл заявки» появляется, когда локальный файл есть.

ФАЙЛЫ
-----
public/pages/transport-ops.html          — readonly снят (КЛИЕНТСКИЙ)
src/routes/transportOperRoutes.js        — PUT сохраняет оба ID (СЕРВЕРНЫЙ)
public/js/modules/transportOpsDocs.js    — комментарий getPayload (КЛИЕНТСКИЙ)

УСТАНОВКА
---------
1. Остановить сервер.
2. Заменить файлы (сохранить структуру папок: src/..., public/...).
3. Запустить сервер (файл transportOperRoutes.js — серверный,
   перезапуск ОБЯЗАТЕЛЕН).
4. На странице обновить кэш браузера (Ctrl+F5).

КАК ПОЛЬЗОВАТЬСЯ
----------------
1. «Редактор транспортных операций» → выбрать операцию.
2. Вкладка «ДОКУМЕНТЫ» → в поле «ID» у нужной службы записки ввести
   d_kod документа из вазовской системы ЭДО.
3. Нажать «Редактировать» (сохранение операции) — ID записан в базу.
4. Дальше по этому ID работают «Ред.» (текст на портале) и «Откр.»
   (карточка документа в браузере). Ошиблись вводом — сотрите значение
   и снова «Редактировать».

ПРОВЕРЕНО
---------
• API: PUT сохраняет оба ID (в т.ч. обрезку пробелов), прочие поля строки
  не затрагиваются, очистка работает; состояние строки после тестов
  восстановлено побайтово (SQL-снимок);
• UI (playwright): readonly снят у двух полей (контрольные поля по-прежнему
  только для чтения), ручной ввод + «Редактировать» → тост «обновлена»,
  после повторного входа значения из базы, guard-и «Письмо уже было
  создано»/«СЗ в СБ уже была создана» работают (двойное создание
  исключено, сетевых вызовов нет), консоль браузера чиста;
• регрессия: t85 35/0, t84 19/0, t83 25/0, t82 32/0, t81 28/0, t80 37/0,
  t79 63/0, t74 82/0, t76b 50/0, t63b смоук OK.

Требуется t74+…+t85.
